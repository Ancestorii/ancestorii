### Left for the owner
- Memory reports have no proper home. They are now recorded in `audit_log` so duplicates are caught, but the reporter's reason only exists in the email to support@. If you want to see memory reports in the app or keep the reasons, the DB agent should add a small `memory_reports` table (memory, reporter, reason, created_at) and this route can switch to it in two lines. Recommended, low effort.
- Story moderation fails open. If the Anthropic API is down, slow (over 30 seconds) or answers nonsense, the story is published without a check. That keeps authors unstuck but means spam or hate could go live during an outage. The alternative is to hold such stories as "pending review" and email you (the author already gets a "please allow up to 24 hours" email in that state). I recommend holding rather than publishing: outages are rare and you review within a day anyway. One-line change in moderate-story when you decide.
- Reported stories only reach you by email. The admin tab on the Profile page lists stories in "pending review" and "rejected"; community reports do not appear there and the story stays live until you act. Options: leave as is, or have the report route move a story with N reports (say 3) to "pending review" automatically. Your call on N.
- Invited users and onboarding. The sign-in callback deliberately skips onboarding for someone who accepted an invite, but `Profiles.onboarding_complete` stays false, so their next login sends them through "first memory" anyway (it posts into the family they joined, nothing breaks). If the skip is intended, accept-invite and join-via-link should set `onboarding_complete = true` after a successful join. Recommended for consistency.
- What moves when a solo user joins a family. accept-invite (like join-via-link) moves the person's memories, memory media, comments and reactions into the new family, then deletes the solo family. Albums, timelines, capsules, loved ones, library files, books, canvases and prints created in the solo family are not moved: their foreign keys to `families` have no cascade, so the solo family delete silently fails and that content is stranded in a family nobody belongs to. Today new users are pushed to join quickly, so this is rare, but a user who built a library and then accepts an invite would lose sight of it. Options: move everything (a dozen tables), or block accepting an invite when the solo family holds content and explain why. I recommend moving, done by the DB agent as one RPC.
- AI cost ceiling. I added 40 requests per user per hour on both assist routes as a safety net. Genuine use is a handful of clicks; say if you want it higher or lower.
- Model and price. The routes use Claude Sonnet 4.6 (3 dollars per million input tokens). Newer and cheaper options exist (Sonnet 5.5 at 2, Haiku 5.5 at 0.10 which would suit the moderation check). Changing the model changes tone slightly, so it is your call; a one-string change per route.
- Reward code messages. The checker tells the user whether a code exists but belongs to another family ("belongs to a different family"), which confirms a code is real. It is useful for honest mistakes; if you prefer not to confirm existence, make that case read like "not recognised". No rate limit exists on this endpoint (signed-in users only).
- The signup email check (`/api/validate-email`) is anonymous and calls a paid service. Anyone could hammer it and burn Kickbox credits. A rate limit at the edge (Vercel WAF rule or Upstash) is the usual answer; nothing in code can fully solve it.
- Admin identity lives in two places: `src/lib/adminUser.ts` and three RLS policies on `featured_stories` hardcode the same user id. Changing the admin means changing both.
- No dead routes: every route in my scope has at least one caller.

### Risks
- Invite by email: Our Family, Invite, enter an address, Review, Send. Expect the toast "Invite sent", an email, and the row in family_invites. Then send the same address again: expect "An invite has already been sent to this email". Temporarily unset RESEND_API_KEY locally and send to a fresh address: expect the toast "We could not send the invitation email" and no row left behind.
- Accept an invite while signed in as a solo user (the QA account qualifies): open the invite link, Join. Expect to land on /dashboard/our-family inside the inviting family with memories moved; open the same link again: expect "This invite has already been used".
- Story notifications: as user B, like, comment on and share user A's published story. Expect A to get one like notice, one share notice, one notice per comment, and a comment email quoting the real comment. Like, unlike, like again: still one like notice.
- Report a story and a family memory as a non-author: expect the dialog to close, one support email each, and a second attempt to answer 409 (the dialogs show nothing on 409, see shared-file notes).
- Publish a story from /stories/create: expect the review step to end on the story page. Then, as admin, reject it and have the author edit and publish again: expect the "under review" screen, an admin email, and no auto-publish.
- Story Assistance card: on a loved-one page with assistance on, the pill appears after a short moment; turn assistance off in Profile, revisit: no pill. Memories editor unchanged. Click Try another twice quickly: only the last answer shows.
- Admin tab: Reject a pending story once, then reject it again (refresh and repeat if the row is gone): the author should have exactly one strike.
- Timeline export: open the Export drawer signed in: PDF preview as before. Call /api/timelines/<id>/export signed out: 401 text.

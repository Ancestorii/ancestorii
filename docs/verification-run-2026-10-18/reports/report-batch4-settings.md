### Fixed

**Settings (app/dashboard/settings/page.tsx)**
- `settings/page.tsx:107` (the 406): the preferences read used `.single()`; a fresh account has no notification_preferences row (confirmed: the QA account has none, and nothing creates one at signup; handle_new_user() creates Profiles, a family, a membership and a Free subscription only). Now `.limit(1).maybeSingle()`. Verified by SQL and reasoning.
- `settings/page.tsx:97-114` (the 400): when the read failed, the page ran `upsert(..., { onConflict: 'user_id' })`. The live table has only the primary key on `id`, a foreign key on `user_id` and a plain (non-unique) index `idx_notification_preferences_user_id`; Postgres refuses `ON CONFLICT (user_id)` without a unique constraint, which PostgREST returns as 400. The page then fell through to a fake row with `id: 'temp'`, so every later Save did `.eq('id', 'temp')` (another 400, swallowed) and the user saw nothing happen. Now nothing is written on load; the row is created on the first Save (plain insert) and updated by its real id afterwards (`settings/page.tsx:136-157`). Verified by SQL (pg_constraint, pg_indexes) and tsc.
- `settings/page.tsx:112`: the default for a missing row was `in_app: false`. The column default is `true` and send-push treats a missing row as opted in, so the switch showed "off" while the real state was "on", and (had the insert worked) merely opening Settings would have opted the user out of push. Default is now `true`. Verified against supabase/functions/send-push/index.ts:111-121.
- `settings/page.tsx:136-152`: the update now ends in `.select('id').maybeSingle()`, so a silent 0-row update (RLS) reads as a failure, and any failure shows a toast ("Could not save your settings. Please try again.") instead of nothing. The marketing opt-in metadata update still runs after a successful row save, and the "Preferences updated successfully." line only appears on success.
- `settings/page.tsx:87`: `auth.getUser()` (a network round trip) replaced by `auth.getSession()` (local), per the brief. Load is now one query. The misindented block inside `save` was re-indented as part of rewriting that function (no other formatting touched).

### Left for the owner
- **Phone support line.** The Help page tells Premium members to ring 0330 133 2268, 9:00am to 6:00pm, Monday to Saturday, and promises a reply to the form "within 24 hours". Please confirm the number is live and staffed in those hours; if not, I recommend removing the phone card (the email line stays) rather than leaving a number nobody answers.
- **Who counts as Premium for phone support.** The page now follows the sidebar: the person who pays is Premium; other members of their family are shown as Free (they see "Upgrade to access priority phone support" even though their family already pays). If you want the whole family covered, that is a product decision that also affects the sidebar badge and the Plans page; say so and the lead can route it.
- **The "Updates & Memory Tips" switch promises something nothing acts on yet.** It is stored (auth metadata `newsletter_opt_in` and `notification_preferences.email`), but no email code reads either value: onboarding-drip sends to everyone with an unsubscribe link, and the newsletter does not exist as a system. Options: wire the drip and any future mailing to honour it (recommended before you rely on it), or reword the card as "we will use this when we launch tips emails".
- **The "In-App Notifications" switch only controls phone push.** Only send-push reads `in_app`; the bell and the Updates list show everything regardless. The card copy says "Be gently notified when meaningful updates happen inside your family library". Either reword to "Push notifications on your phone", or have the bell honour it too (a shell change). I recommend the reword; it is honest and cheap.
- **Deleting an account on the web.** The public /delete-account page says "Open the Ancestorii app, go to your Profile, tap Delete Account, confirm". On the website there is no Delete Account button on Profile or Settings; the only path is emailing support. A `delete-account` Edge Function exists in the live project (not in the repo, no caller in this codebase: it is presumably the mobile app's). A browser cannot delete an auth user by itself; a web button would have to call that function. Decide whether the web needs the button (I recommend yes, since the legal page already promises it and the function exists), or change the legal page to say "in the mobile app" explicitly.
- **Changing the email address.** Profile shows the email disabled with "Managed through your login provider". There is no email-change flow anywhere in the app (Supabase supports one with a confirmation email). If members ask for it, that is a new feature; if not, the current wording is fine.
- **Password rules.** Settings accepts any password of 6 or more characters with no confirmation field and no current-password check. Fine for now; if you want stronger rules (8 or more, or a confirm field) say so.
- **FAQ promises to confirm or soften:** "If a payment fails, we retry and notify you before any limits apply." (Stripe retries; I could not verify that the member is notified before limits apply.) "More sharing and permission features are coming soon." (A promise with no date.) Both at help/page.tsx:162 to 190.
- **The contact Edge Function (send-contact-email) lives only in Supabase, not in the repo.** Its emails are hand-written HTML outside the shared letter renderer every other email uses, the member's confirmation subject contains an em dash ("Your message has been received, Ancestorii Support"), it promises "usually within 24 hours", and it imports Deno std without a version pin. I recommend the Edge agent brings it into supabase/functions on the shared shell. Nothing on the page needs to change for that.
- **Avatar size.** The cropped photo is uploaded at the crop's full pixel size (a 4000px phone photo becomes a 4000px avatar, several MB) and the bucket has no file size limit; the page only caps the original at 10MB. Down-scaling to about 512px in src/lib/cropImage.ts would make every avatar load faster everywhere. Small, safe, not urgent.
